01

The model

Every gap in the analysis reduced to one missing idea: the platform had no concept of delegation. It checked whether you could perform an action, never whether you were entitled to pass that power on.

An administrator is not a category of person. They are a holder of a bounded set of privileges over a bounded part of the tree, and everything they do to another account must stay inside both bounds. Three invariants express that, and every provisioning route is now built from them.

Invariant 1

You cannot give away more than you hold

Any privilege granted must already be held by the grantor. Applies wherever privilege moves: assigning a role, inviting a user, creating a role, editing a role, onboarding an organization.

Invariant 2

You can only build beneath yourself

A new entity must hang from one you already administer, and its shape must be legal beneath its parent's shape.

Invariant 3

Nothing bypasses the scope resolver

Every data path resolves tenant scope the same way. Tooling that cannot — because it reads raw tables — is restricted to the operator's own tenants instead.

Why all three, together

Each invariant alone leaves a hole. Without I1 a branch administrator promotes themselves to platform power. Without I2 that power grafts entities into other customers' trees. Without I3 the promotion reaches every tenant's raw data regardless. They were designed and shipped as one change.

02

I1 · Capability ceiling

One function, five call sites. The rule is a set comparison: the privileges a role grants must be a subset of the privileges the grantor holds. 

excessCapabilities(actorId, actorTenantId, requested) → string[]
  platform-scope actor (SAAS / SAAS_UNIT) → []        // root of trust
  otherwise                                → requested \ held

Platform operators are exempt by design. They must be able to provision a customer's Billing Admin without holding billing rights themselves — that is the job. Every tenant-scoped actor is bound, and the exemption is decided by tenant type, which a role change cannot alter.

That last detail is what makes the rule airtight. An attacker who somehow acquired a powerful role would still sit in a BRANCH tenant, and so would still be measured against the ceiling.

I2 · Structural containment

Tenant creation was the one hierarchy operation that never resolved scope. It now checks both that the parent is yours and that the resulting shape makes sense.

Gate A
Is the parent inside your scope?

Resolved the same way list, read and delete already did.

PARENT_OUTSIDE_SCOPE
Gate B
Is this shape legal beneath that parent?

The lattice below. The error names what is allowed.

INVALID_HIERARCHY
Gate C
Root entities are operator-only

A tenant with no parent has nothing containing it, so only the platform can create one.

PARENT_REQUIRED

The shape lattice

SAAS → HOLDING · MULTIBRANCH · BRANCH · FRANCHISE · PARTNER · SAAS_UNIT HOLDING → MULTIBRANCH · BRANCH MULTIBRANCH → BRANCH FRANCHISE → BRANCH (a location) PARTNER → MULTIBRANCH · BRANCH (client workspaces) SAAS_UNIT → nothing (an internal function owns no customers) BRANCH → nothing (a leaf stays a leaf)

Self-service, now that it is safe

With both gates in place, create-or-manage-a-tenant was granted to Group Admin, Organization Admin, Franchisor Admin and Partner Owner. A holding group adds its own subsidiaries; a franchisor adds its own locations. Neither can touch anyone else's tree.

It was also removed from Pre-Sales Manager. Spinning up a demo and provisioning a production subsidiary were the same operation, held by a commercial role — the wrong default.

04

I3 · Scope uniformity

The database console reads and writes every table directly. It cannot pass through the scope resolver, so it is restricted by tenant type instead — the one property a role change cannot touch.

It now sits behind two independent gates: the caller's tenant must be SAAS or SAAS_UNIT, and they must hold the security capability. Either alone was insufficient — capability was the gate that the escalation chain walked straight through.

Verified 
Branch Admin → /api/admin/db/table/User
   PLATFORM_ONLY: This is a platform operations tool and is not
   available to tenant accounts.

Platform Super Admin → same route
   operator still has access (67 rows)

Before this change, the same request from an escalated branch account returned 67 user rows spanning 8 tenants.

05

Atomic onboarding

Creating an organization and creating its first administrator were two unrelated calls. They are now one transaction that cannot half-succeed. 

POST /api/tenants/onboard
{
  "name": "Najd Industrial",
  "type": "MULTIBRANCH",
  "parentId": "…",              // optional; required for non-operators
  "planId": "…",                // optional
  "admin": { "email": "…", "name": "…", "roleId": "…" }
}

The administrator block is mandatory — omitting it returns ADMIN_REQUIRED, because an organization nobody can enter is not an outcome worth supporting. Entity, subscription, first administrator and the audit record either all land or none do.

Credential lifecycle

The temporary password is generated with a CSPRNG, hashed with bcrypt, returned exactly once for out-of-band delivery, and now expires after seven days. An invitation that was never taken up stops being a way in.

Expiry is checked only after the password itself verifies, so the response never reveals whether an account exists to someone guessing.

Verified 
onboard without an admin block:        ADMIN_REQUIRED
onboard complete organization:        success, one transaction
new admin logs in with temp password: logged in, mustChangePassword=1
same credential, expiry backdated:    TEMP_CREDENTIAL_EXPIRED
