01

Onboarding an organization today

There is no "onboard an organization" operation. There are two unrelated API calls that a Super Admin performs in sequence, and nothing binds them together.

01
Create the tenant

Name, operating model, optional parent, optional plan. The materialized path is built from the parent so the hierarchy is queryable. A subscription row is created if a plan is named.

POST /api/tenants
{ "name": "Al Noor Holding Group", "type": "HOLDING", "planId": "…" }
requires: create-or-manage-a-tenant
02
Create their first administrator

A separate call. Generates a random temporary password, hashes it with bcrypt, sets mustChangePassword, and returns the plaintext once so the operator can pass it to the customer by some other channel.

POST /api/iam/users/invite
{ "email": "…", "name": "…", "roleId": "…", "tenantId": "…" }
requires: add-a-user-with-role-based-access
03
They sign in and are forced to rotate

The temporary password works exactly once for a login; every protected route then returns 428 until the password is changed.

What the platform does well here: the password is never stored in plaintext, rotation is compulsory, the invite is tenant-scope-checked, and both actions are written to the immutable audit trail.

The join is missing

Nothing links step 1 to step 2. Creating a tenant produces an empty organization with no users and no way in. If the operator stops there — or the second call fails — the tenant exists, bills, and appears in every list, but nobody can log into it. There is no check anywhere that a tenant has at least one administrator.

02

What each shape needs after onboarding

This is where the model breaks down. Every shape below expects to grow its own structure — and none of them can.

Once onboarded, they need to…Admin roleCan they?
Holding group adds a subsidiaryGroup AdminNo — lacks the privilege
Franchisor adds a franchisee locationFranchisor AdminNo
Company adds a branchOrganization AdminNo
Consultancy adds a client workspacePartner OwnerNo
Regional office adds an entityRegional AdminNo
Add users to their own entityAll of the aboveYes
Assign and change rolesAll of the aboveYes — without limit, see §3
Move users between entitiesAll of the aboveYes

The privilege create-or-manage-a-tenant is held by exactly three roles, all of them on the operator's side of the relationship: Platform Super Admin, Customer Success Manager, and — oddly — Pre-Sales Manager in the Partner portal.

So a bank that onboards with three regions and later opens a fourth cannot create it. A franchisor signing its fiftieth location cannot add it. Every structural change becomes a support request to you. That is a viable model for a white-glove pilot and an untenable one at scale — it makes your revenue growth linear in your own support headcount.

03

The escalation chain

The most serious finding. Each link is individually defensible; together they let the lowest-tier administrator on the platform reach every tenant's data. I ran this against the running system.

1

A Branch Admin — scoped to one branch, the smallest admin role — holds maintain-roles-and-permissions so they can manage their own team.

2

The role-assignment endpoint checks tenant scope and blocks self-promotion, but has no privilege ceiling. It never asks whether the assigner holds what they are granting.

3

So they assign Platform Super Admin to a colleague in their own branch. The call succeeds.

4

That colleague now holds monitor-security-and-handle-incidents, which is the only gate on the database console.

5

The database console performs raw table access with no tenant scoping. It reads — and writes, and deletes — every row on the platform.

Verified against the running system 
3. ESCALATION A — promote them straight to Platform Super Admin:
   Role changed to "Platform Super Admin"

=== escalated Branch user reading the User table via DB console ===
   READ 67 user rows spanning 8 tenant(s)

One nuance worth stating precisely, because it limits the damage: tenant scope is resolved from the user's tenant type, not their role. The promoted user's normal API calls still resolve to SELF — they see one tenant through /api/tenants. The breach is not through the scoped API. It is the database console, which bypasses the scope resolver entirely.

There is a second, independent route to the same place: role creation has no ceiling either. A Branch Admin can mint a custom role granting create-or-manage-a-tenant, govern-a-feature-flag and monitor-security-and-handle-incidents — none of which they hold — and assign it. Closing only the assignment path would leave this one open.

Why this matters commercially

A multi-tenant GRC platform sells on the promise that one customer cannot see another's control failures. This chain breaks that promise, and it is reachable by a role you would hand to a branch office manager without a second thought. Any prospect's security review will test exactly this.

04

All seven gaps

Critical

Role assignment has no privilege ceiling

verified

Any holder of maintain-roles-and-permissions can assign any system role, including Platform Super Admin, to any user in their scope. Eight roles hold this privilege, down to Branch Admin. Scope and self-promotion are checked; the grant itself is not.

Critical

Role creation has no capability ceiling

verified

Custom roles are validated for existence of capability keys, never for whether the creator holds them. A Branch Admin successfully created a role granting three privileges they do not have.

Critical

The database console is not tenant-scoped

verified

Every other read passes through the scope resolver. The console does not — it is direct table access gated on a single capability, with full write and delete. It is what turns a role-assignment mistake into a platform-wide data breach.

High

Tenant creation never checks the parent is yours

verified

Listing, reading and deleting tenants all resolve scope first. Creating one does not — it validates that the parent exists and stops there. A Pre-Sales Manager in one organization successfully created a tenant underneath an unrelated holding group, which then appears inside that group's hierarchy and rolls up into its reporting.

Verified 
=== a real Pre-Sales Manager creating a tenant under someone else's group ===
   CREATED under Al Noor — parentId never scope-checked
High

No customer can grow their own hierarchy

verified

No tenant-level role holds create-or-manage-a-tenant. Holding groups, franchisors, organizations and partners must all raise a request with you to add a subsidiary, location, branch or client workspace. This is the gap you asked about, and it is a product limitation rather than a defect — but it caps how far the platform can scale without your staff in the loop.

Medium

Onboarding is not atomic

Tenant, subscription and first administrator are three independent calls. A failure between them leaves an orphaned tenant that nobody can enter and nothing detects. There is no "tenant has no administrator" check anywhere in the platform.

Medium

Credential delivery is manual

The temporary password is returned in the API response for the operator to convey out-of-band. That is a defensible design — it is certainly better than emailing a password — but it is a human step with no expiry on the credential and no record of whether it was ever delivered. A brand-new user also cannot receive the in-app notification that now exists, because they have not logged in yet.

05

What to change

In priority order. The first three are small and close the critical chain; the fourth is the product change that lets the platform scale.

1 · Cap what an administrator can grant

On both role assignment and role creation, reject any capability the actor does not themselves hold. This single rule closes two of the three critical findings, and it is the standard expectation in any RBAC system — you cannot give away more than you have.

2 · Scope the database console

Either run its queries through the tenant scope resolver like every other read, or restrict it to the platform tenant so no customer-side role can reach it however they were promoted. The second is simpler and probably correct: it is an operator tool, not a customer feature.

3 · Scope-check parentId on tenant creation

Three lines, mirroring what update and delete already do: resolve the actor's scope and reject a parent outside it. Also worth reconsidering whether Pre-Sales Manager should hold tenant creation at all — a demo tenant and a production subsidiary are the same operation today.

4 · Let customers grow their own hierarchy

Grant tenant creation to Group Admin, Franchisor Admin, Organization Admin and Partner Owner — but only once fix 3 is in, so they can only create beneath themselves. Constrain it further by shape, so the tree stays meaningful:

An admin of…May create beneath themselves
HOLDINGMULTIBRANCH, BRANCH
MULTIBRANCHBRANCH
FRANCHISEBRANCH (a location)
PARTNERClient workspace tenants
BRANCHNothing — a leaf stays a leaf

Pair it with a plan-based ceiling on entity count, and hierarchy growth becomes a self-service upsell rather than a support ticket.

5 · Make onboarding one operation

A single call that creates the tenant, its subscription and its first administrator in one transaction, returning the temporary credential. Nothing half-created, and no tenant that nobody can enter.
