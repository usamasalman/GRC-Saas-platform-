01

What GRC Wisdom is

Most compliance work fails not because nobody did it, but because nobody can prove it later. Evidence lives in a shared drive, the risk register is a spreadsheet somebody last opened in March, and when the regulator asks who approved a control exception, the answer is an email thread.

GRC Wisdom replaces that with a system where every assurance activity leaves a record that stands up to scrutiny. It holds your standards and controls, tracks who implemented what and with which evidence, runs the internal audit lifecycle end to end, and funnels every issue — wherever it came from — into one register with common ownership and aging.

It is built around three ideas that shape every screen:

  • Separation of duties is enforced, not advised. The person who raises a finding cannot close it. The person who remediates cannot validate their own remediation. These are server-side rules that return an error, not guidance in a policy document.
  • The audit trail is tamper-evident. Every consequential action writes a hash-chained entry. Altering history breaks the chain visibly.
  • Derived values are never client-supplied. Residual risk is computed from the effectiveness of linked controls. A KRI's status is computed from its thresholds at write time. Nobody can type in the answer they want.
02

Why an organization adopts it

Four situations drive adoption. Most organizations arrive with one and discover the others.

You have to certify against a standard

ISO 27001, SOC 2, NCA Essential Cybersecurity Controls, Saudi PDPL — all four ship seeded, with clause-level mapping. One control can satisfy clauses across several standards simultaneously, so you implement once and report against each framework separately. When the auditor asks "show me how you meet A.5.15", the platform answers with the control, its owner, its evidence, and its last validation date.

A regulator, board or client demands independent assurance

The internal audit module implements the real lifecycle: a risk-scored audit universe, an annual plan that must be justified by risk and approved by someone other than its author, fieldwork with a risk-and-control matrix and sampled testing, working papers with independent review sign-off, and findings that management must formally answer.

You operate across entities and need consolidated oversight

A holding group, a franchise network, a bank with regional branches, or a consultancy running several client workspaces all need the same thing: local teams doing local work, with a group view that aggregates without letting entities read each other. The tenancy model handles this directly rather than through workarounds.

You want the risk picture to be evidence-based rather than anecdotal

Risk appetite set by the board actually blocks acceptance of risks beyond tolerance. Key risk indicators raise issues automatically when they breach. Realised losses are recorded against the risks that were supposed to prevent them — so you can check whether your register was ever realistic.

03

Choosing your shape

The first decision is your operating model. It determines what each user can see, and it is not cosmetic — the scope resolver enforces it on every read.

ModelWho it fitsVisibility
SAAS The platform operator itself Every tenant. The control plane.
SAAS_UNIT Internal business units of the operator — billing, marketplace, security services Platform-wide, scoped to their function
HOLDING A group with legally distinct subsidiaries Itself and everything beneath it
MULTIBRANCH One legal entity with branches or departments Itself and its branches
BRANCH A single site, region or department Only itself
FRANCHISE A franchisor mandating a baseline across independent franchisees Network-wide, with exception workflows
PARTNER Consultancies and MSPs running client workspaces Their own portfolio of client tenants
Choose carefully

The common mistake is picking HOLDING when you mean MULTIBRANCH. Use HOLDING only when the subsidiaries are separate legal entities that could be sold independently. If they are branches of one company, use MULTIBRANCH — group reporting works the same way, but the compliance boundary is drawn correctly.

A further 10 roles cover specialised tenant functions — Internal Auditor, Control Owner, Asset Owner, Vendor Owner, Consultant, Client Administrator and Client Contributor among them.

How permission actually resolves

Every protected route names the capability it requires. A user's role grants a set of capability keys; if the key is missing the request fails with CAPABILITY_DENIED and names the capability, so the error tells an administrator exactly what to grant. Users with no role resolve to an empty set — the system fails closed.

Worth knowing

Capability and separation of duties are two different gates and both apply. Holding the right capability does not exempt you from the conflict rules — a GRC Manager who holds both assess-and-treat-a-risk and plan-and-execute-an-audit is still blocked from validating a corrective action they themselves owned.

Getting started

Run the API

cd grc_wisdom_api
npm install
npx prisma generate
npx tsx src/seed.ts     # builds the demo dataset
npm run dev             # http://localhost:3000

The API needs a .env with DATABASE_URL and a JWT_SECRET of at least 32 characters. Copy .env.example and generate a secret with node -e "console.log(require('crypto').randomBytes(32).toString('hex'))". The server refuses to start without one rather than falling back to a default key.

Run the web app

06

The modules

Each block below states what the module is for, who uses it, and how much of it you can reach from the interface today.

In the UI usable from the web app · API only built and tested, no screen yet · Not built navigation exists, behind it is placeholder data

Governance foundation

Document & policy management

In the UI

Compliance Manager, Compliance Approver, Staff Employee

Author policies, route them for approval, publish, and track who has acknowledged reading them. Versions are retained; the audit log is immutable and hash-verifiable. Retention schedules and legal hold prevent deletion of documents under investigation.

Use it when you need to demonstrate that staff were told about a policy and confirmed it — the single most common evidence request in a certification audit.

Standards library

In the UI

GRC Manager, Compliance Officer

Enable the frameworks that apply to you. ISO 27001, NCA ECC, Saudi PDPL and SOC 2 ship with 28 clauses seeded between them. Enabling a standard for a tenant makes its clauses available for control mapping and reporting.

Control library

In the UI

GRC Manager, Control Owner

20 seeded controls with 39 clause mappings. The mapping is many-to-many by design: control AC-01 satisfies ISO27001:A.5.15, NCA-ECC:2-2-1 and SOC2:CC6.1 at once. This is what stops you rebuilding your whole control set for each new framework.

Implementations & evidence

In the UI

Control Owner, GRC Manager

A control in the library is a template. An implementation is that control actually running in your organization, with an owner, a status, an effectiveness rating, a next-review date, and attached evidence. Effectiveness here is what drives residual risk everywhere else.

Risk

Risk register

In the UI

Risk Manager, Risk Owner

5×5 scoring — likelihood by impact, giving 1 to 25. Inherent score is what you assess. Residual is computed, never typed: each linked control that is Verified and Effective reduces likelihood by 2, PartiallyEffective by 1, capped so residual never falls below 1. Deleting your controls raises your residual risk automatically, which is the point.

Creating a risk triggers a mandatory duplicate search — the platform returns similar existing risks and you must acknowledge them before it will create another. Acceptance is time-bound and requires a reason, and the risk owner cannot approve acceptance of their own risk.

Risk appetite

API only

Board, Executive, Risk Manager

The board sets, per risk category, an appetite threshold (carry it without further approval) and a tolerance threshold (the absolute ceiling). Both sit on the same 1–25 scale as residual scores. A statement stays a draft until someone other than its author approves it — an unapproved appetite gates nothing.

Once approved it has teeth. Attempting to accept a risk scoring beyond tolerance fails: 

BEYOND_RISK_TOLERANCE: RSK-006 has a residual score of 16,
beyond the approved tolerance of 15 for Technology. A risk this
far outside appetite must be treated down, not accepted.

Key risk indicators

API only

Risk Manager, Control Owner

Metrics with amber and red thresholds, linked to the risks they signal. Each KRI declares whether higher or lower is worse — stored explicitly, because inferring it silently inverts every alert. Thresholds are validated against that direction, so a "higher is worse" indicator cannot be saved with red below amber.

One reading per period, immutable once recorded, so the trend cannot be quietly rewritten. A red reading raises an issue automatically. An indicator nobody acts on is decoration.

Loss events

API only

Risk Manager, Finance Manager

Risks that actually materialised, in Basel operational-risk categories, with gross and recovered amounts and both the date it happened and the date you found out. That gap — detection lag — is itself a control-effectiveness signal, and the register reports the average.

A net loss at or above 50,000 raises an issue automatically so the control failure gets remediated rather than absorbed.

Risk & control self-assessment

API only

Control owners, first line of defence

Periodic campaigns where control owners attest to their own controls. Draft the campaign, add controls to scope, launch it, collect attestations, close it. Scope freezes at launch. Only the assigned respondent can attest. Attestations are not revisable, and a campaign cannot close while any response is outstanding.

A control self-reported as ineffective raises an issue automatically — the whole value of self-assessment is that first-line admissions reach the register without waiting for an audit to find them.

Internal audit

Audit universe & annual plan

API only

Chief Audit Executive, Internal Auditor

The universe is everything that could be audited, scored on six weighted factors: financial materiality (25%), regulatory exposure (20%), complexity (15%), change volatility (15%), prior findings (15%) and fraud exposure (10%). Entities never audited receive an uplift, as do overdue ones — so neglect raises priority rather than hiding it.

The annual plan is built from that scoring and cannot be approved while a high-risk entity is left uncovered. Capacity is checked against available hours. The preparer cannot approve their own plan, and an approved plan is immutable — changes go through a documented deferral.

Fieldwork, testing & working papers

API only

Internal Auditor, Audit Manager

Each engagement carries a risk-and-control matrix: the risks in scope, the controls that address them, and the procedures that test those controls — with sampling method, population and sample size recorded.

Results are immutable once recorded, and the conclusion must be consistent with the evidence: recording exceptions while concluding "Satisfactory" is rejected. Working papers require independent review — the preparer cannot sign off their own, and review notes must be cleared before sign-off. An engagement cannot reach Reporting until every paper is reviewed.

Audit programme

In the UI

Internal Auditor, GRC Manager

Engagements through their lifecycle — Planned, Fieldwork, Reporting, Closed — with findings raised in the IIA structure of criterion, condition, cause and recommendation, plus management response and corrective action tracking.

Issue register

In the UI Partly

Everyone with something to fix

One register for issues from all six sources: internal audit, external audit, regulators, self-identification, incidents and risk assessment. Common aging, escalation and ownership regardless of origin — a regulator finding has no audit engagement, so trapping findings inside audits was the structural mistake this fixes.

Aging is derived, never stored, so it cannot go stale. Default remediation windows are 30 days for High, 60 for Medium, 90 for Low, overridable per issue.

Audit-raised issues appear inside the Audit Programme screen with full response and closure workflow. The standalone cross-source register — where you would log a regulator letter — is API-only for now.

Operations

Service desk (ITSM)

In the UI

Everyone; managed by Support Coordinator

Tickets with ITIL 3×3 priority derived from impact and urgency, service catalogue with workflow routing, SLA policies with an escalation scanner that runs every five minutes, and a knowledge base. Public comments and internal work notes are deliberately separate — the customer sees one and not the other.

Users, teams & access

In the UI

Organization Admin, HR Manager

User directories per tier, team and department structure, the full 42-role permission matrix, and lifecycle operations — joiners, movers, leavers, and transfers between branches or entities.

Tenants & impersonation

In the UI

Platform Super Admin

Provision tenants, set their operating model, and manage the hierarchy. Support staff can impersonate a tenant user to reproduce a problem — sessions are time-boxed, fully logged, and strictly read-only: every write is rejected while impersonating, so support can never act as a customer.

Security services, marketplace, billing, vendors

Not built

—

Wisdom Eye attack-surface management, Eye Phish simulation, the module and open-source tool marketplaces, subscriptions and invoicing, and third-party risk management all appear in the navigation but are backed by placeholder data. Treat these as roadmap, not capability.

07

The golden thread

The modules are not separate products. The value is in how a single problem travels through them — this is the walkthrough worth doing on your first day.

01
A standard imposes a requirement

ISO 27001 A.5.15 requires documented authorisation for privileged access.

02
A control answers it

Control AC-01 is mapped to that clause — and simultaneously to NCA-ECC 2-2-1 and SOC 2 CC6.1.

03
Someone implements and owns it

An implementation is created with an owner, evidence, and an effectiveness rating.

04
Risk residual moves on its own

The unauthorised-access risk links to that control. Because it is Verified and Effective, residual likelihood drops by 2. Nobody typed that number.

05
Appetite decides whether you may live with it

If residual still exceeds the board's approved tolerance for that category, acceptance is refused outright.

gate · BEYOND_RISK_TOLERANCE
06
Assurance tests whether it really works

Three routes reach the same place: internal audit samples it during fieldwork, the control owner attests in an RCSA campaign, or a KRI breaches its red threshold.

07
An issue is raised — from whichever direction

All three land in the one register, alongside regulator letters, external audit findings and incidents.

08
Management must formally answer

Agree, Partially Agree or Disagree — with their own action plan. No corrective action can be assigned until they do, and the person who raised it cannot write the response.

gate · NO_MANAGEMENT_RESPONSE
09
Remediation, then independent validation

The corrective action owner remediates and submits evidence. Someone who is neither the raiser nor the remediator validates and closes it.

gate · SOD_VIOLATION
10
And if it did not hold

Reopening voids the previous management response. Remediation failed, so management must go on record again before a new plan is accepted.

If management disagrees

A Disagree response does not get a corrective action plan — it becomes Disputed and moves to escalation instead. Two levels exist: executive management, then the audit committee. That is the real route an auditor takes when management will not accept a risk the auditor considers material, and pretending otherwise would make the register dishonest.

08

What makes it defensible

These are the mechanisms an external assessor will probe. All are enforced server-side and return errors, not warnings.

Separation of duties

Five data-driven rules ship enabled, plus explicit checks at each decision point:

  • The author of a document cannot approve it
  • The requester of access cannot approve it
  • Whoever raised an issue cannot close it
  • The owner or operator of a control cannot independently validate it
  • Whoever submits an invoice adjustment cannot approve it

Beyond those: the corrective action owner cannot validate their own remediation, the preparer of a working paper cannot sign it off, the drafter of a risk appetite cannot approve it, the risk owner cannot approve acceptance of their own risk, and the auditor who raised a finding cannot write management's response to it.

Tamper-evident audit trail

Every consequential action writes a hash-chained entry inside the same transaction as the change itself — so the record and the action either both happen or neither does. The external auditor portal can verify the chain cryptographically.

Immutability where it matters

Test results, KRI readings, RCSA attestations and closed issues cannot be edited. Approved audit plans are frozen. This is what makes a historical trend or a testing conclusion worth anything.

Tenant isolation

Every query is scoped through the resolver before it runs. Cross-tenant reads by group-level roles are legitimate but logged as such, so consolidated oversight never becomes silent access.
