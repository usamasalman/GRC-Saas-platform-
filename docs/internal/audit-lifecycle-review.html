Review · Audit Lifecycle Plan vs the Running System

Most of this is already built. The gaps are elsewhere.

An assessment of the proposed Enterprise Audit Lifecycle plan against the code that actually runs today — what already ships, what the plan misses, three miscited standards, and one verified defect that undermines the plan's central premise.

01

Verdict

The plan describes six of its seven phases as work to be done. Six of them shipped and are covered by passing tests. Presenting them as proposals would mean rebuilding what already runs.

PhaseStatusEvidence
1 · Universe & risk scoringBuilt/universe, six weighted factors, never-audited uplift
2 · Annual risk-based planBuilt/plans/:id/approve, preparer ≠ approver, capacity check, high-risk coverage gate
3 · Engagement scopingBuilt/plan-items/:itemId/instantiate
4 · RCM, testing, workpapersBuilt/matrix/:rowId/procedures, /workpapers/:wpId/review, conclusion-consistency and open-note gates
5 · Findings & management responseBuilt/issues/:id/respond, auditor barred from responding
6 · CAP & independent closureBuilt/issues/:id/close, raiser and remediator both barred
7 · Final report & committee sign-offAbsentNo report endpoint, model, or opinion field anywhere

The SoD matrix in the plan is accurate and matches what the server enforces — with one understatement. The plan says closure bars the raiser and the CAP owner; the code also bars whoever recorded the management response, which is the stricter and more defensible rule.

Where the real work is

The backend is roughly four slices ahead of the interface. Phases 1, 2 and 4 have no screens at all — no audit universe page, no annual plan page, no risk and control matrix, no workpaper view. The plan's proposal to add five tabs to AuditProgramme.tsx is the single most valuable item in it, and it is the only frontend item.

02

The critical defect

The plan's premise is seven sequential phases. The engagement state machine does not enforce sequence at all — it validates that a status is a member of a list, never that the transition is legal.

Reproduced against the running system 
created: AUD-2026-04 (Planned)

Planned -> Closed, no fieldwork, no workpapers, no findings:
   ALLOWED — now Closed  (workpaper gate bypassed)

Closed -> Fieldwork:
   ALLOWED — reopened to Fieldwork

The workpaper review gate is real, but it only fires when the target status is Reporting. Set the status straight to Closed and the engagement never passes through it. An audit can therefore be signed off with no evidence file, no testing, and no review — which is precisely the failure mode the gate was written to prevent.

Closed engagements can also silently reopen. There is no record that it happened, no reason captured, and no distinction between "reopened because the file was deficient" and a mis-click.

Why this outranks everything else in the plan

Every other gate in the audit module is sound. This one hole makes them optional, because the path around them is a single field update that the API accepts. Any external quality assessment would test exactly this, and the plan does not mention it.

The fix is small: declare the legal transitions and reject the rest, requiring a reason and an audit entry for any backwards move. 

Planned    → Fieldwork | Cancelled
Fieldwork  → Reporting | Cancelled
Reporting  → Closed
Closed     → (terminal; reopening is a new follow-up engagement)

Three miscited standards

Worth correcting before this reaches a customer. If you claim conformance with the 2024 Standards, an assessor will know these references.

Plan saysActuallyCorrect reference
Fieldwork & workpapers = 12.1–12.3 Principle 12 is Enhance Quality — the quality assurance and improvement programme Conducting engagement work is Principle 14; engagement documentation is 14.5
Engagement scoping = 11.1 Principle 11 is Communicate Effectively with stakeholders Engagement planning is Principle 13 (13.1–13.6)
Findings = 14.1 14.1 is Gather Information for Analysis and Evaluation Communicating results is 15.1; confirming implementation is 15.2

Phase 1 and 2 cite 9.4 for the risk-based plan, and that one is right.

04

What the plan misses

Five elements the 2024 Standards treat as mandatory, none of which appear in the plan or the codebase. Two of them are prerequisites for claiming conformance at all.

Internal audit charter Absent

Principle 6 requires a board-approved charter establishing the function's authority, scope and reporting lines. It is the document an assessor asks for first. There is no model for it, no approval workflow, and no link from engagements to the mandate authorising them.

Quality assurance and improvement programme Absent

Principle 12 requires ongoing internal assessment, performance measurement, and an external assessment at least every five years. A platform that hosts the audit function but cannot evidence its own QAIP cannot support a conformance claim. This is the largest single omission — and commercially the most interesting, because it is exactly what a Chief Audit Executive is asked for by their board.

Auditor independence and conflict declarations Absent

Domain II requires objectivity to be managed, not assumed. Nothing records that a lead auditor declared no conflict with the entity under review — for instance, having previously worked in it. The platform enforces separation of duties between individuals on a record, which is not the same thing as engagement-level independence.

Engagement conclusion Absent

Std 15.1 requires the final communication to state a conclusion. The Audit model has objective, scope and criteria but no opinion or rating field. Findings aggregate to counts, never to a judgement. An audit report that lists issues without concluding whether the control environment is adequate is not a report.

Follow-up as a distinct activity Partial

Std 15.2 requires confirming that management acted. Reopening an issue exists, but there is no follow-up engagement type and no scheduled re-test. Verification currently depends on someone remembering to look.

05

Platform-specific gaps

No reporting layer at all

Phase 7 is entirely unbuilt: no report model, no draft-to-final workflow, no distribution list, no export. The generate-and-distribute-a-report capability exists in the role matrix and gates nothing. For an assurance product this is the most visible absence — the report is the deliverable the customer actually pays for.

No audit committee

The plan names the audit committee as plan approver and report recipient. There is no committee entity, no membership, and no board-reporting concept. Approval currently resolves to any user holding a broad capability, which is not the same as a governing body accepting a plan.

Budget hours are planned but never consumed

AuditPlanItem.budgetHours and AuditPlan.totalBudgetHours exist and capacity is checked at approval — but nothing records actual hours. Resource management under Principle 10 needs planned against actual, and without it the following year's capacity planning is guesswork.

Sampling is recorded, not evaluated

Sample size, population and method are captured, which is more than most systems do. Nothing checks that the sample is defensible for the population, and nothing carries an exception rate forward into a conclusion about the population as a whole.

External auditors cannot actually be scoped to an engagement

The External Auditor role exists and the portal is read-only, but access resolves through the tenant scope resolver rather than an engagement grant. An external auditor either sees the tenant or does not — you cannot admit a firm to one engagement's evidence and nothing else, which is how external audit access is normally sold and controlled.

06

What I would do instead

The plan's sequencing spends most of its effort re-verifying working code. This ordering fixes what is broken, then builds what is missing, then makes it visible.

1 · Close the state machine hours

Declare legal transitions, reject the rest, require a reason for any backwards move. Without this every other gate in the module is optional. Nothing else in the plan matters more.

2 · Engagement conclusion small

Add an opinion to the engagement — adequate, needs improvement, inadequate — required before Reporting, with a narrative. Cheap, and it turns a list of findings into an audit.

3 · The five-tab interface the real work

This is the plan's best idea and I would keep it as written. It surfaces four slices of tested backend that currently have no screens. One correction: the existing Create Audit button bypasses the approved-plan gate the backend enforces, so the Engagements tab should create only from plan items.

4 · Reporting and distribution new build

Report model, draft to final workflow, recipient list, export. This is Phase 7 and it is the customer-visible deliverable.

5 · Charter, QAIP, independence new build

The conformance layer. Until these exist the platform supports doing internal audit but cannot evidence that the function itself is run to the Standards — which is what a board asks for.

On the verification plan

The proposed audit-test.sh covers ground already covered. Scripts under scripts/verify/ already test finding closure, SoD rejection, independent closure and reopening. Rather than re-testing those, the script worth writing asserts the illegal transitions are refused — which is the thing that currently fails.
