02

The decision to make

Extraction from a PDF is never perfectly reliable. What matters is what the platform does with an imperfect result, and there are two defensible answers.

Option A · Staged review before commit recommended

Extraction produces candidates in a staging area. Nothing enters the standards library until a person accepts each clause — editing refs and titles where the parse went wrong. The commit is a deliberate act, attributed and audit-logged.

The reason this matters is specific to your product: a misparsed clause that silently enters the library becomes the criterion an auditor tests against, and every finding raised under it inherits the error. The evidence trail would look complete and be wrong. Staging keeps a human accountable for what the framework says.

Option B · Direct import

Extraction writes straight into the standard, and the user corrects mistakes afterwards in the authoring screen. Faster for clean documents, and the audit trail still records who imported what. The risk is that nobody reads 93 clauses after the fact, so errors persist unnoticed.

I recommend A. It is roughly a day more work and it is the difference between a convenience feature and one that survives an external quality assessment.

Not proposed: LLM extraction

It would parse messy layouts better than patterns can, but it adds per-document cost, a non-deterministic result that two runs may disagree on, and an external data path for documents that are often confidential. Deterministic parsing plus human review is the more defensible starting point. If clause detection proves too weak on real documents, an optional model-assisted pass is a clean addition later — behind the same staging gate.

03

Import architecture

01
Upload

Base64 in JSON, matching the pattern documentController already uses — no new multipart handling, and the file lands in the existing uploads/ directory.

02
Extract text

PDF via pdf-parse, DOCX via mammoth, Excel and CSV via exceljs. Spreadsheets are the easy case — columns map directly to fields.

03
Detect clauses

Pattern matching tuned to how real standards number themselves — A.5.15, 1.2.1, CC6.1, Art. 11, 2-2-1. Each candidate carries a confidence derived from which pattern matched and whether a plausible title followed it.

04
Review

Accept, edit or reject each candidate. Low-confidence rows surface first, because those are where a parse goes wrong. Nothing has entered the library yet.

05
Commit

Accepted candidates become clauses on a new or existing standard, in one transaction, with an audit entry naming the source file. Duplicate refs are refused, exactly as the manual path already refuses them.

Controls import the same way, with a different candidate shape — code, title, objective, domain — and the same staging and commit steps. A spreadsheet with a clause-reference column can additionally propose mappings, which the reviewer confirms.

New models

FrameworkImport      file, type, status, counts, uploader, target standard
ImportCandidate      ref, title, text, confidence, status, edited values

Both are staging tables. Neither is read by any assessment path, so a half-finished import cannot affect an audit.

04

Export architecture

One report service, three renderers. The content of a report is decided once; the format is a presentation choice made at the end.

ReportContentsFormats
Risk & Control MatrixEngagement risks, linked controls, procedures, sampling, results, exceptionsExcel · PDF · DOCX
Audit reportObjective, scope, criteria, conclusion, findings in IIA structure, management responses, CAP statusPDF · DOCX · Excel
Issue registerCross-source issues, aging, escalation, ownershipExcel · PDF
Standard & control libraryClauses, mapped controls, coverage gapsExcel · PDF
Annual planUniverse scores, plan items, capacity, approval recordExcel · PDF

Excel is the working format — auditors live in spreadsheets, and an RCM exported to Excel is immediately useful. PDF is the issued artefact. DOCX is for reports that go on to be edited before committee.

Two things the exports must carry

  • Provenance. Every export is stamped with who generated it, when, from which tenant, and the engagement status at that moment. A report printed from a Fieldwork engagement must say so rather than looking final.
  • The capability finally used. generate-and-distribute-a-report exists in the role matrix and currently gates nothing. These endpoints are what it is for, which removes one of the twenty-one inert privileges.
Export is a disclosure path

Every export is scope-resolved before rendering. A group role exporting an issue register gets its subtree and nothing wider, and the cross-tenant read is logged as one — the same rule every other read already follows. Without that, export becomes the way around tenant isolation.

Libraries

Five are installed already — pdf-parse, mammoth, exceljs, pdfkit, docx. All are pure JavaScript with no native build step, which matters on Windows. I chose exceljs over SheetJS deliberately: the npm build of xlsx carries prototype-pollution and ReDoS advisories, which is not a dependency a compliance product should ship.

06

Proposed order

Sequenced so each step is independently verifiable, and so the defect that undermines reporting is closed before reports exist.

01
Ordered state machine + engagement conclusion

Hours. Closes the review's critical defect and gives the audit report something to conclude. Everything after this is safe to export.

02
Excel import and export

The highest value per hour. Spreadsheets are unambiguous to parse, and an RCM in Excel is what an auditor actually wants. Proves both pipelines end to end.

03
PDF and DOCX extraction with staged review

The harder parsing, behind the review gate. Includes the candidate review interface.

04
PDF and DOCX report rendering

The issued artefacts, with provenance stamping and the capability gate.

05
The five-tab audit interface

From the original lifecycle plan — surfaces four slices of tested backend that still have no screens, and is where the export buttons naturally live.
